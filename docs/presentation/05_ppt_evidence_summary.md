# 식수센스(SNP) 최종발표 PPT — 근거 중심 핵심 성과

대상: 충북대학교 소프트웨어학부 졸업작품, 2026년11월15분 최종발표 준비. 조사일2026-10-19. 사용자 제공 프로젝트 배경과 실제 코드/Git/기존 시험 증거를 구분한다.

## 발표에서 가장 강한 핵심 메시지

> 식수 예측을 참고 정보로 제공하고, 영양사가 확정한 식수에서 출발해 납품규격 발주·합격량 입고·재고 사용·현장 문서까지 연결한 업무 시스템이다.

‘AI가 모든 발주를 자동화했다’ 또는 ‘전체 요구사항/현업 인수100% 완료’는 현재 근거보다 강하다. ‘3개 학기 프로젝트’는 사용자 배경 설명이며 현재 Git은2026년3월부터 확인된다. 3개 학기 전체의 실험·기능 이력을 커밋으로 모두 복원한 것은 아니다.

## 강조할 핵심 성과 8개

### 1. 발표용 제목: 영양사 업무를 하나의 데이터 흐름으로 연결

- 핵심 메시지: 식단·레시피→최종 식수→발주예정서→업체별 주문→검수→재고·수불을 동일 모델 관계로 연결했다.
- 실제 근거: `a8d9fae`, `procurement/workflow.py`, 모델 FK/JSON 스냅샷; [브라우저 거래 결과](../../verification/requirements/browser.json), [통합 테스트](../../integration_tests/test_requirements.py).
- 추천 화면/시각화: 업무 흐름 화살표와 각 단계의 저장 ID, 발주예정서·검수·주간 수불 화면. 도식은 [시스템 구조](04_system_architecture.md) 활용.
- 발표 주의: 공급업체 실제 전송·ERP·분할 납품·회계 확정까지 구현한 전체 ERP라고 하지 않는다. 14단계 모든 CRUD 브라우저 전수 시험이 끝난 기록은 없음.

### 2. 발표용 제목: AI 예측과 영양사의 최종 결정을 분리

- 핵심 메시지: AI는 참고값이고, 발주 기준은 영양사가 확정한 날짜·끼니별 식수다. AI가 없어도 업무를 계속할 수 있다.
- 실제 근거: `DietPlan.final_headcount`, `save_headcount`, `AttendancePrediction`, 업무 허브의 수동/AI/최종 열; `test_ai_absent_manual_confirmation_and_ui`, `test_final_confirmation_overrides_ai` 및 저장 모델 추론 로그.
- 추천 화면/시각화: 같은 날짜의 직접 예상·AI 참고·최종 확정3열과 변경 후 재검토 표시. 식수351→352 변경에35.1→35.2kg이 갱신되는 기존 [조리지시서 결과](../../verification/cooking-format/browser.json).
- 발표 주의: 정상 SBERT 임베딩 경로·시간 분리 정확도는 미검증. 영양사보다 정확하다는 수치나 폐기량 절감률을 만들지 않는다.

### 3. 발표용 제목: kg 필요량을 실제 납품 포장수로 환산

- 핵심 메시지: 업체별 내용량·단위·발주 간격을 명시해 단순 kg 표를 실제 구매수량으로 바꾼다.
- 실제 근거: `SupplySpecification`, `build_preview/confirm_orders`, 단위 오류/누락/700g/소수kg 회귀. T3에서351명×100g=35.1kg,5kg/캔→최소8캔, 사용자가9캔 조정.
- 추천 화면/시각화: `351×100g → 35.1kg → /5kg → ceil=8캔` 도식과 포장규격 관리·발주 수량 입력 화면.
- 발표 주의: 35kg→7통은 **해당 품목이5kg/통인 경우**다. 포장 크기를 이름에서 추정하지 않는다. ‘1인당3개×개당70g’ 전용 환산까지 완성했다고 하지 않는다.

### 4. 발표용 제목: 검수 합격량만 입고하고 중복 처리를 막는다

- 핵심 메시지: 발주 완료 버튼과 실제 입고를 구분하고, 합격 수량만 원장에 반영한다.
- 실제 근거: `GoodsInspection`, `inspect_item`, OneToOne 입고 로그·UUID와 트랜잭션; 같은 검수 재전송·상충 수정·검수 전 입고 금지 테스트.
- 추천 화면/시각화:45kg 납품→40kg 합격/5kg 제외→40kg 입고,35.1kg 사용 후4.9kg 잔량의 수치 흐름. [수불 캡처](../../verification/requirements/browser-ledger.png).
- 발표 주의: 이 숫자는 격리 시험 데이터다. 부분 합격과 다회 분할 납품은 다르다. 동시 부하·운영 장애까지 완전한 중복 방지를 입증한 것은 아니다.

### 5. 발표용 제목: 신규 재고의 FIFO와 주간 수불을 추적

- 핵심 메시지: 원장 합산과 lot 배정으로 사용 내역·잔량·기한을 검토한다.
- 실제 근거: `inventory/lot_services.py`, `StockLot/StockAllocation`, `workflow_views.py:ledger`; oldest receipt/expiry·주간 기초10+입고2−폐기1=기말11 테스트.
- 추천 화면/시각화: 두 lot에서 오래된 순으로 사용하는 간단 도식, 주간 수불의 기초/입고/사용/폐기/조정/기말 열.
- 발표 주의: 기존 모든 재고가 lot에 대사됐다는 뜻 아님. 유통기한 사전 알림·자동 폐기 기능까지 주장하지 않는다.

### 6. 발표용 제목: 실제 영양사 양식을 소프트웨어 출력으로 연결

- 핵심 메시지: 제공된 조리지시서6시트를 분석하고6열·병합·페이지 설정을 반영하되 계산 근거는 별도로 보존했다.
- 실제 근거: 원본 Excel, `verification/cooking-format/reference-analysis.json`, 미커밋 `meals/cooking_export.py`, 실제 원본 구조 비교 테스트와 [브라우저 인쇄 PDF](../../verification/cooking-format/browser-print.pdf).
- 추천 화면/시각화: 원본6열과 생성6열 나란히, 재료별 비고 입력→Excel→인쇄의 연속 캡처. [생성 Excel](../../verification/cooking-format/browser-cooking.xlsx).
- 발표 주의: 원본 입고일 묶음·대상집단별 식수까지 완전히 재현하지 않았다. 1인량·계산근거는 시스템 추가 항목. 이 코드는 현재 **미커밋**이고 기존 서비스 배포 증거는 없음.

### 7. 발표용 제목: 기존 기능을 보존하며 가을 개선을 통합

- 핵심 메시지:9월 기능 개선과 기존 Sprint7 업로드·재고 차감·대시보드를 합치고 실제 오류를 보정했다.
- 실제 근거: `3b01dc8`→`eac48a0`→`e21478b`→`a8d9fae`, release_patch URL 보존·calc_stock/단일ID·안전재고 회귀; [변경 전후 표](02_2026_fall_changes.md).
- 추천 화면/시각화:6월 기준·9월 개선·10월 통합·미커밋 양식 개선의4구간 타임라인, 단위/검수/최종식수 스키마 변화.
- 발표 주의: 보존 커밋 날짜를 코드 최초 개발일로 표시하지 않는다.9월8일 기능 브랜치 변경이 곧9월말 피드백 반영이라는 인과관계도 확인 불가다.

### 8. 발표용 제목: 시험으로 확인한 범위와 남은 과제를 함께 제시

- 핵심 메시지: 기능 존재가 아니라 저장·계산·예외·권한을 격리 DB와 실제 브라우저 산출물로 확인했다.
- 실제 근거: [SQLite117개](../../verification/cooking-format/sqlite.log) / [MariaDB117개](../../verification/cooking-format/mariadb.log), JS4개, 조리지시서16개 포함, migration check와 데이터 업그레이드 시험.
- 추천 화면/시각화: 검증 표(동일117개 사례를 두 DB에서 실행), 오류/중복/단위/권한/FIFO 분류, 실제 성공 로그의 마지막 Ran/OK와 PDF 캡처.
- 발표 주의: 두 DB의117개를 독립 기능234개라고 세지 않는다. 조리지시서16개는117개에 포함된다. 196행 추적표는 상하위 중복 태스크여서 기능196개/완성률로 표현하지 않는다. 이번 발표 조사에서 새로 재실행한 결과는 아니다.
