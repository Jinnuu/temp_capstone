## 주요 검증 내용

### 승인·권한

- auto 가입 화면 안내, 실제 폼 가입 후 즉시 로그인, 기본 DIETITIAN, 위조 role/is_superuser 무시. manual은 비활성 PENDING으로 유지.
- 기존 비활성을 모두 대기로 추정하지 않음. 확인된 대상만 분류/승인. 정지/비활성/탈퇴의 일괄 승인은 거부.
- 정지 후 올바른 비밀번호 로그인 차단 및 기존 브라우저 세션의 업무 접근 차단. 해제 후 로그인 가능.
- 일반 사용자 관리자 목록/상세/매트릭스/감사/직접 GET·POST API 및 native admin 접근 거부. CSRF 없는 관리자 POST 거부.
- 다중 역할 저장/재조회, 기존 세션에 권한 회수 즉시 반영, VIEWER의 쓰기 차단, COOK의 조리지시서 저장, 재고/영양사 역할 분리.
- 관리자 본인 변경, 일반 앱 관리자의 superuser 변경, 알 수 없는 역할, 오래된 revision, 정의되지 않은 필드, 공급업체 내부 역할 부여, 탈퇴 복구를 거부.
- MariaDB의 두 관리자 동시 상호 강등: 성공 1건/거부 1건, 활성 관리자 1명 유지. 실패 감사 로그도 남음.
- 성공·거부 이벤트의 작업자/대상/전후 상태/역할을 확인하고 비밀번호가 기록되지 않음을 assertion으로 확인.
- Django admin 사용자/그룹 원시 추가·변경을 차단하여 보호 규칙 우회를 방지.

### 기존 업무 및 복구

브라우저에서 관리자 역할로 거래처와 명시적 납품규격을 준비한 후 **DIETITIAN 역할**로 식단·레시피 업로드/수정, 기존 AI 모델 추론, 수동 360명과 최종 351명 분리, 필요량/포장 계산, 업체별 발주, 검수 합격량, 재고 사용/FIFO/주간 수불, 조리 지시사항 저장·Excel/PDF, 정산을 실제 폼으로 수행했다. 조리 입력 후 재고 표가 동일함을 비교했다. 결과는 `business/browser-result.json`의 각 수치 assertion과 출력 파일에 있다.

계정 복구는 이전 구현과 동일한 브라우저 시나리오를 새 증거 경로에서 재실행했다. 격리 SMTP 수신함에서 아이디 소유권 링크와 복수 계정 비밀번호 재설정 메일을 수신했다. 확인 전 아이디 비공개, 확인 링크 1회 사용, 약한 비밀번호 거부, 새 비밀번호 저장/로그인, 사용한 재설정 링크 재사용 차단을 확인했다. **외부 실제 수신자에게 메일이 도착한 검사는 아니다.**

## 발견·수정 및 검사 준비 문제

1. 기존 데이터 migration 테스트가 inventory/procurement만 되돌린 상태에서 accounts의 옛 ORM으로 insert하여 새 필수 컬럼과 불일치했다. `old_targets`에 accounts/0001을 포함해 역사적 모델과 실제 스키마를 맞췄다. NOT NULL 제약을 약화하지 않았다.
2. 기존 권한 테스트의 302는 decorator의 로그인 리디렉션이었다. 새 서버 RBAC의 명시적 403을 기대하도록 바꿨다. 접근 거부 요구를 완화하지 않았다.
3. 신규 검사 첫 실행의 존재하지 않는 URL을 실제 등록 URL로 수정했다. 브라우저 시작 대기, 복수 체크박스 선택, 두 아이디의 부분 문자열 중복 선택을 하네스에서 수정했다.
4. 격리 SQLite 메일 작업자가 다른 컨테이너의 `/tmp`를 보던 준비 오류가 있었다. 작업자를 테스트 앱과 같은 파일 시스템에서 실행해 SMTP 수신을 재검증했다. 실제 Preview는 공용 MariaDB를 사용하며 이 오류의 대상이 아니다.
5. 가입 설명이 항상 관리자 승인을 요구하던 문구를 환경 정책에 맞게 바꾸고 auto 모드 화면 assertion을 추가했다.
6. 반복 공개 로그인 검증이 기존 Nginx 요청 제한에 걸려 503을 받았다. 제한을 끄거나 바꾸지 않고 로그인 페이지 접근 간격을 늘린 하네스로 최종 재검증했다. SMTP 미설정에 따른 복구 POST 503은 별도로 기대하는 동작이다.

초기 실패 및 민감할 수 있는 진단은 Git 제외 `.ui-preview/audit/rbac-20261105/`에 보존했다. 최종 로그가 이전 실패가 없었다는 뜻은 아니다.

## 공개 HTTPS 최종 검증

`https://ui.jinnuu.site`에서 기존 시범 영양사 로그인/세션 재조회/Secure 쿠키, 실제 식재료·메뉴 검색 JSON API, POST 로그아웃, CSRF 거부, 세 모드 인증/복구 화면과 자동 가입 안내를 확인했다. 시범 관리자로 세 모드의 권한 표와 감사 화면을 열고 두 대상 계정의 승인 완료 상태를 실제 사용자 목록에서 확인했다. 새 실계정 생성이나 실제 비밀번호 변경은 하지 않았다. 로그인 요청 제한은 유지했다. 최종 13개 지점 모두 통과, 브라우저 JS 오류 0이다. `public-*-matrix.png`는 실계정 목록 대신 개인정보 없는 역할 표를 캡처했다.

## 실제 계정과 데이터

기존 8개 계정의 ID·아이디·비밀번호 해시·이메일·legacy role·staff/superuser 플래그를 백업 복원 데이터와 직접 비교했다. 두 확인된 가입 계정만 활성 상태를 변경했고 감사 승인 이벤트가 각 1개 존재한다. 다른 기존 비활성 계정은 확인 필요 상태로 남겼다. 작업 중 외부 신규 가입이 관찰되었으며 삭제하거나 테스트 데이터로 바꾸지 않았다. 신규 계정은 관리자 플래그가 없는 일반 영양사다. 최종 수는 보존 검증 JSON을 따른다.

`wlsdngur12`, `swwlsdngur12`는 서버 인증 허용 상태로 확인했다. **두 소유자의 실제 비밀번호로 로그인하지 않았으며 비밀번호를 요청/추측/변경하지 않았다.** 올바른 기존 비밀번호로 소유자가 직접 최종 확인해야 한다. 기존 이메일이 비어 있으면 SMTP를 설정해도 이메일 복구를 사용할 수 없다.

## 보호 범위와 잔여 사항

- Preview DB와 복구 캐시 컨테이너 자체, 8000/8007/8010 컨테이너의 ID·이미지·PID·시작 시각·마운트·네트워크 동일성을 비교했다. 모든 포트 로그인 페이지 200. Preview DB 내용은 요청대로 migration·역할 초기화·대상 승인만 적용했다(외부 신규 가입 별도).
- 5개 Preview 서비스 healthy. 배포는 `snp-ui-preview`의 web/recovery-mail/proxy만 `--no-deps`로 교체했다. 터널 설정·운영 볼륨·네트워크를 바꾸지 않았다.
- 기존 인증 backend 이름의 세션은 재로그인이 필요하다. 비밀번호는 유지된다.
- SMTP 미설정: 실제 외부 메일 수신은 **미검증**. 발송 성공으로 표시하지 않는다.
- 공통 헤더의 기존 계정 구분 표시는 보존하며, 실제 다중 업무 역할/유효 권한은 관리자 상세에서 확인한다. 일부 기존 조회 화면의 동적 수정 컨트롤은 서버 403으로 차단되며 전체 화면의 역할별 버튼 배치를 재설계한 것은 아니다.
- 이번 검사는 역할/CSRF/일부 XSS 및 무결성 회귀이며 전체 침투·부하·접근성 인증은 아니다.
- 관리자 목록/로그는 최대 200개와 검색/상태 필터를 제공한다. 대규모 조직용 페이지네이션, 고급 감사 내보내기·보존 정책, 세부 권한 편집, 신원 확인 이메일 변경, 별도 조리 상태 추적은 추가 구현하지 않았다.
- Preview 공개 가입 기본 역할은 영양사다. 운영 전환 시 manual 정책과 별도의 권한·개인정보 검토가 필요하다.
- 실행 명령과 파일별 변경 이유는 `verification/rbac-20261105/README.md` 및 `RBAC_AND_APPROVAL.md`를 참조한다. 커밋은 UI 브랜치에만 로컬 생성하며 원격 push는 하지 않는다.

## 임시 자원 정리 및 커밋 범위

작업 소유권/네트워크를 확인한 테스트 앱·프록시·메일 캡처·Redis·tmpfs MariaDB 5개와 임시 네트워크를 정리했다. 실제 Preview 서비스 5개는 유지했다. `test-resource-ownership.json`과 `cleanup.log`에 기록했다. 비공개 복구 백업/이전 이미지 태그는 보존했다. Git 후보 파일에서 실제 secret 값과 기존 계정의 비밀번호 해시·등록 이메일이 없는지 검사했으며, 원본 문서·백업·환경 파일은 커밋하지 않았다.
