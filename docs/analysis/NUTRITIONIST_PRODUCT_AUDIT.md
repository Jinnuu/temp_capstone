## 1. Executive Summary

**판정: 단일 급식시설의 핵심 업무를 설명하는 통제된 졸업작품 시연은 가능하다. 실제 현업의 일상 운영을 전적으로 맡길 준비가 됐다고 판단할 근거는 부족하다.** 식단·확정 식수·명시적 포장규격·업체별 발주·공급업체 응답·검수 합격량 입고·FIFO·수불·조리지시서로 이어지는 정상 경로가 구현되고 자동화 증거가 있다. 반복 분할 납품, 검수 정정, 취소/재발주, 회계 기준, 과거 문서 보존 및 실제 사용자 인수에는 공백이 있다.

이번 조사에서는 제품 코드·테스트·DB·권한·비밀번호·Docker 구성을 변경하지 않았다. 실제 서비스에 로그인하지 않았다. 로그인 자체도 세션/최근 로그인 시각을 바꾸기 때문이다. 공개/로컬 로그인 GET, Preview DB의 비민감 필드 SELECT, 코드와 기존 로그/화면 열람, DB 없는 일회용 컨테이너 모의 실행만 수행했다. 새 전체 회귀·브라우저 업무 시나리오는 실행하지 않았다.

특히 다음을 새로 확인했다.

- 기존 공급업체 계정 편집 경로가 새 관리자 대상 보호를 호출하지 않는다. 공급업체 겸 SUB_ADMIN인 기존 발주처 계정을 다른 SUB_ADMIN이 편집할 수 있는 논리를 DB 없는 모의 실행으로 재현했다. 비밀번호/권한 탈취를 재현한 것은 아니다.
- 식수 보고서가 수동 예상 식수를 실제 식수로 취급한다. 따라서 표시된 오차율을 실측 예측 정확도로 발표하면 안 된다.
- 발주 상세는 일률적으로 10%를 가산하지만 월간 정산은 세금 기준 미등록을 표시한다. 상품별 과세/면세를 확인하지 않은 상태에서 최종 정산금액으로 사용할 수 없다.
- 식단 일괄 업로드에는 사용 확정 식단 수정 방지 검사와 기존 발주 재검토 표식의 일관성이 보이지 않는다. 정적 분석 위험이며 실제 DB 재현은 하지 않았다.
- Preview 공개 자동 가입은 실제 영양사 신원 확인이 아니다. 초기 seed는 시범 최고관리자와 일반 시범 계정에 같은 비공개 초기 비밀번호를 사용하도록 작성돼 있다. 현재 비밀번호의 동일 여부는 조회하지 않았다.

이번 문서는 영양사 현장 인수 결과가 아니다. 시설 특성에 따른 영양·알레르기·예산·정산 요구는 **현업 확인 필요**다. 모든 체크리스트 항목을 무조건 신규 개발 필수로 판단하지 않는다.

### 관리자 계정과 안전한 접근

2026-11-06 실제 Preview DB에서 비민감 필드와 그룹만 SELECT한 결과다.

| 아이디 | MAIN_ADMIN | superuser | 활성 | 승인/RBAC | 로그인 가능 조건 |
|---|---|---|---|---|---|
| `verify-admin` | 유효 역할 MAIN_ADMIN, `SNP_ROLE_MAIN_ADMIN` 소속 | 예; staff도 예 | 예 | ACTIVE, rbac_managed=True | 기존의 올바른 비밀번호, 정상 CSRF/쿠키, 로그인 제한 미초과 |

이 조회 범위에서 다른 MAIN/SYSTEM_ADMIN 그룹·legacy ADMIN·superuser 후보는 없었다. 이 계정의 legacy role은 ADMIN이며 유효 역할은 MAIN_ADMIN이다. `SYSTEM_ADMIN`은 코드에서 MAIN_ADMIN으로 호환되며, 현재 별도 SYSTEM_ADMIN 그룹 관리자는 확인되지 않았다. 새 앱 MAIN 역할 자체가 Django staff/superuser를 부여하지는 않는다(`accounts/rbac.py:roles`, `accounts/admin_requests.py`).

- 로그인: `https://ui.jinnuu.site/accounts/login/`에 `verify-admin`과 소유자가 아는 기존 비밀번호 사용. 이번 조사에서 비밀번호 성공 여부는 검증하지 않았다.
- MAIN 화면: `/accounts/manage/dashboard/`, `/accounts/manage/requests/`, `/accounts/manage/permissions/`, `/accounts/manage/audit/`. 공통 RBAC 미들웨어와 `admins.manage`/`accounts.manage`, 대상 보호가 적용된다. native `/admin/`은 MAIN 기능 외에 Django staff 조건도 필요하다. 뒤의 기존 공급업체 경로 결함은 별도 예외다.
- **비밀번호 원문은 DB에서 조회할 수 없다.** 해시는 원문 복구 수단이 아니다. 해시·토큰·세션·secret 파일을 출력/공유하지 않는다.
- 먼저 계정 소유자/프로젝트 책임자와 서버 운영 권한을 확인한다. 시범 공용 안내가 있더라도 관리자 비밀번호를 일반 시연자에게 재공유하지 않는다.
- 현재 외부 SMTP는 `disabled`다. 이메일 비밀번호 찾기 화면이 있어도 실제 외부 발송/수신은 불가하다. 향후 검증된 SMTP와 소유권 확인 이메일이 준비되면 기존 복구 절차를 사용할 수 있다.
- 비밀번호를 모르면 **소유권 확인 및 별도 변경 승인 후**, 운영자가 아래 대화형 명령으로 기존 계정만 재설정할 수 있다. 명령은 안내일 뿐 이번에 실행하지 않았다. 비밀번호를 명령 인수·환경 출력·채팅에 넣지 않는다. 재설정 후 기존 세션은 Django 인증 해시 검사에 따라 다음 요청에서 무효가 된다.

```sh
cd /home/woohyeak/sprint7-integration
docker compose -p snp-ui-preview --env-file .ui-preview/compose.env \
  -f compose.ui-preview.yml exec web python manage.py changepassword verify-admin
```

신규 `admin` 생성, 기존 관리자 비밀번호/권한 변경은 이번 범위가 아니며 별도 승인이 필요하다.

## 2. SNP 현재 구현 범위

Django Template + 점진적 TypeScript/Vite UI, Django 인증/ORM, MariaDB, Redis 복구 큐, Nginx, 기존 학습 모델로 구성된다. Green/Civic/Reference 모드는 동일 URL·데이터를 사용한다. Preview는 별도 DB/네트워크/볼륨을 사용한다. AI 모델 파일과 추론 코드를 이번에 변경하지 않았다.

구조상 적합한 초기 범위는 **한 시설의 식단·식수·자재·구매·검수 보조**다. 여러 학교/사업장의 데이터 격리, 병원 치료식, 학생별 알레르기 대응, 기관별 회계 결재를 제공한다고 설명하면 안 된다. 대상 시설과 계약 범위를 정한 후 필요성을 결정해야 한다.

## 3. 실제 영양사 업무 프로세스

권장 연결은 기준정보/규격 → 식단·레시피 → AI 참고/수동 예상 → 식사별 최종 식수 → 재료 합산/재고·안전재고 → 명시적 포장 환산 → 업체별 발주 → 업체 응답/납품 계획 → 구매자 검수 합격량 → 로트 입고 → 사용/FIFO/수불 → 조리지시서/정산이다.

업무 의미를 구분해야 한다.

- AI 예측, 수동 예상, 최종 확정, 실제 급식 인원은 서로 다른 값이다. 현재 앞의 세 값은 구분되나 실제 인원의 보고서 연결은 잘못돼 있다.
- 수주 수락·출고는 입고가 아니다. 합격량 확정 시에만 재고가 증가한다.
- 납품 예정 수량·실제 납품 수량·합격량은 별개다. 한 차수 부분 수량은 처리하지만 반복 분납/미납 잔량 관리가 완결되지 않았다.
- 발주예정서·주간 레시피 명세서·조리지시서는 별도 문서다. 조리지시서 메모 저장은 재고 사용 확정이 아니다.
- 발주 합계와 월 검수 합계는 날짜 기준과 수량이 다를 수 있다. 세금·정정·마감이 없는 합계는 회계 확정값이 아니다.

## 7. 데이터 정합성 및 보안 평가

### 실제 읽기 전용 표본

현재 Preview는 사용자 9명, 메뉴 5개, 레시피 4개, 식단 4개, 발주 2개, 검수 2개, 업체 소속 2개, 신규 수주 상태 레코드 0개였다. 메뉴 수와 레시피 수는 서로 다른 엔터티 수다. 레시피가 없는 메뉴 2개가 있다. 사용 식재료의 업체 미지정/일치 규격 누락 각 0개, 양수 재고의 잔여 lot 미연결 0개, 음수 재고 0개, 기한 없는 잔여 lot 3개다. 기한 없는 lot를 모두 부패 식품 오류라고 단정할 수 없으며 품목별 정책 확인이 필요하다. 이 소규모 합성 표본은 현업 전체 데이터의 정합성 보증이 아니다.

### 이번 새 모의 실행 증거

두 검사는 `docker run --rm -i --network none --read-only --tmpfs /tmp --entrypoint python snp-ui-preview-web:three-modes -B -` 형태로 실행했다. Django 테스트 설정과 Mock manager/render/transaction을 사용하고 DB에 연결하지 않았다. 테스트 파일이나 영구 로그는 새로 만들지 않았으며 출력의 비민감 결과를 아래에 보존한다. E1/E2의 회귀 통과 수에 더하지 않는다.

| 검사 | 입력/비교 | 실제 관측 | 판정/한계 |
|---|---|---|---|
| 식수 보고 의미 | 예측 130, manual 120, final 100, 실측 자료 없음 | actual_count=120, error_rate≈8.3333 | 수동 예상값을 실측처럼 계산함. 운영 정확도 지표로 부적합 |
| 레거시 업체 편집 | 행위자 SUB, 대상 canonical SUPPLIER+SUB를 가정. 새 guard와 기존 view 비교 | 새 guard는 거부, 기존 `suppliers` view는 username 변경 후 save 호출·302 | 관리자 대상 보호 경로 차이 확인. 실제 대상 DB 변경/계정 탈취는 수행하지 않음 |

### 보호되는 점

- 기본 Django 세션·CSRF·비밀번호 검증/복구 토큰, 요청 제한·로그 민감 경로 보호가 있다. 공급업체 IDOR, 상태 전이, 수량 범위·수식 삽입 방어와 일부 동시성은 E1/E2/E3 증거가 있다.
- 검수/출고/조리 지시 저장을 재고 변경과 구분한다. decimal·단위 체계·중복 처리·lot allocation을 사용한다.
- 실제 Preview는 manual 기본 정책을 바꾸지 않고 전용 환경 `auto`를 사용한다. 공개 자동 영양사 가입은 의도된 Preview 정책이다.

### 남은 위험

- 레거시 공급업체 프로필 수정은 새 관리자 대상 검사를 공유하지 않는다. `supplier_views._save`의 연결 User 이름/전화 변경 경로도 함께 검증해야 한다. 모의 재현은 `workflow_views.suppliers` 경로만 했다.
- `deploy/ui-preview/seed_preview.py:12–18`은 최초 생성 시 한 demo secret을 관리자/영양사/공급업체에 사용한다. 기존 계정을 덮어쓰지는 않는다. 현재 해시/비밀번호를 비교하지 않았으므로 지금도 동일하다고 단정하지 않는다. 초기 일반 계정 비밀번호가 공유됐으면 관리자도 같은 값인지 소유자가 안전하게 확인하고 분리해야 한다.
- `ACCOUNT_APPROVAL_MODE=auto`에서 유형 선택만으로 내부 영양사 쓰기 권한을 얻는다. 공개 실데이터 운영에는 부적절하다. 전시는 접근 범위를 제한하거나 승인된 고정 시연 데이터/계정만 사용해야 한다.
- Django의 secure cookie 설정은 로컬 HTTP 지원 때문에 false이지만 Nginx가 `ui.jinnuu.site` 호스트에 HTTPS 및 Secure 쿠키를 적용한다. E3 공개 테스트에서 Secure 확인. 설정 false만으로 공개 HTTPS 취약점이라고 단정하지 않는다. 직접 포트·Tailscale·Cloudflare 경로별 운영 정책 검토는 필요하다.
- 역할/업체별 보호가 모든 레거시 수정 URL에 일관되지는 않다. 전수 URL×역할×대상 상태 매트릭스가 필요하다. RBAC 테스트를 전체 침투 테스트로 표현하지 않는다.
- 실제 SMTP 미설정, 정기 원격 백업/복원훈련·RPO/RTO·운영 경보·부하 한계·다기관 데이터 격리는 확인되지 않았다. 과거 수동 백업 복원 성공은 정기 재해복구 체계의 증거가 아니다.

- 메뉴 복사·엑셀 일괄 업로드·취소/정정 중 가장 빈번한 시간 소모는?

## 11. 졸업작품 전시 전 권장 작업

이번에는 구현/설정 변경하지 않았다. 다음 지시에서 승인 후 조치할 전시 게이트다.

- 불특정 사용자가 접속할 전시라면 AUD-01~03을 먼저 해소/통제한다. 관리자와 일반 데모 비밀번호의 분리 확인 없이 안내하지 않는다. 관리자 실계정은 공개하지 않는다.
- 실제 식수/정확도 화면은 AUD-04 해결 전 시연에서 제외하고 AI는 참고값·최종 결정은 영양사라고 설명한다.
- 업로드로 완료 식단을 덮어쓰는 시연은 AUD-05 검증 전 제외한다. 이미 확정/사용된 업무 자료를 재사용해 변경하지 않는다.
- AUD-06 해결 전 발주 상세의 부가세 포함 합계를 확정 지급액으로 설명하지 않는다. 월 정산은 '검토용 집계'라고 표시한다.
- QA/XSS 시험명·누락 레시피·기한 정책을 정리한 별도 합성 전시 데이터를 준비한다. 현재 DB를 삭제/청소하라는 지시가 아니다.
- 정상 전량 입고 한 건을 사용하고 반복 분납/반품·취소는 지원 범위를 명시한다. 스크린샷/Excel/PDF 사본을 오프라인 대체 자료로 준비한다.
- 실제 브라우저에서 새 시연 계정/날짜/순서로 최종 리허설하고 화면 저장 후 재조회, 업체별 격리, 검수 입고량, 수불 계산을 확인한다. 현재 보고서는 새 리허설 통과를 주장하지 않는다.

## 12. 상용화 전 권장 작업

선정한 시설의 업무 범위·책임/승인 규칙을 먼저 확정한 뒤, 취소/정정/추가 납품/반품과 과거 기록 보존을 완결한다. 세금/정산·실제 식수·원가 기준을 검증하고, 요구 범위에 따라 영양·알레르기 데이터와 책임 체계를 구축한다. 공급업체 실재/소속 검증과 내부 직원 신원, 운영 메일·백업·모니터링·접근성·성능 한계·장애복구를 실증한다. 다기관 서비스로 확장할 때 조직 단위 데이터 격리를 선행한다. 현장 영양사·납품업체·조리 담당자 인수 없이 '상용 준비 완료'로 표현하지 않는다.

## 13. 최종 종합 평가

SNP의 강점은 정상 업무의 데이터 연결, 최종 식수와 명시 규격, 합격량 기반 재고, 업체별 포털 및 조리지시서 출력까지 직접 이어지는 구조다. 단순 화면 모음 이상의 통합 구현과 과거 260개 회귀·브라우저 증거가 있다. 반면 테스트 통과가 모든 경로의 안전성과 현장 예외 처리를 보증하지 않음을 이번 두 모의 재현이 보여준다.

**전시: 사전 준비된 합성 데이터와 제한된 정상 경로로 조건부 가능. 현업 무인 도입/공개 다기관 운영: 준비 미완료.** 불특정 공개 사용·관리자 계층/정산/AI 정확도 전 범위 보장을 하려면 위 P0와 관련 리허설을 먼저 해결해야 한다. 실제 업무 생산성·수용성은 현업 확인 필요다.

이번 산출물은 본 문서와 백로그·시연 계획 3개뿐이다. 제품/테스트/참고 문서 변경, 계정/DB 변경, migration, 서비스 재배포/재시작, commit/push는 수행하지 않았다.
