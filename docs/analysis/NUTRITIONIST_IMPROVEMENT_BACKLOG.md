## 우선순위와 평가 척도

- P0: 권한/데이터 오류 또는 핵심 업무 안전성. 공개 범위·사용 조건에 따른 위험은 조건을 명시한다.

- P2: 사용성과 업무 효율 개선.
- P3: 범위 확정 후 장기 확장.
- 점수는 중요도(I)·사용 빈도(F)·오류 영향(R)·구현 난이도(D)·시연 기여(V), 각각 1~5다. 실측 사용자 조사 결과가 아닌 코드/업무 흐름 기반 상대 평가다. 난이도는 높을수록 어렵다.

## AUD-01 — 기존 공급업체 편집의 관리자 대상 보호

- 현재 문제/근거: `accounts/access_views.py:protect_target`는 SUB의 관리자 대상 변경을 막지만 `procurement/workflow_views.py:suppliers`는 이를 호출하지 않고 username/name/phone을 저장한다. SUPPLIER+SUB인 canonical 발주처 계정은 대상 queryset에 포함될 수 있다. `supplier_views.py:_save`의 연결 User 수정도 함께 확인해야 한다.
- 재현: 실제 DB 없는 모의 실행에서 일반 SUB 행위자와 SUPPLIER+SUB 대상을 구성했다. 새 guard는 거부하나 기존 view는 save를 호출하고 302를 반환했다. 비밀번호·권한 변경이나 실제 DB 공격을 한 것은 아니다.
- 기대 동작: 신규/레거시 모든 계정 변경 경로에 동일한 행위자×대상 보호 및 감사 규칙 적용.
- 선행 조건: 공급업체 SUB 겸임 정책 유지, canonical owner/직원 계정 구분. 관련 파일: 위 두 view, `accounts/access_service.py`, `rbac.py`, `supplier_identity.py`.
- 완료 기준: SUB가 자기/다른 관리자 프로필·아이디를 기존 URL/API로도 바꾸지 못하고 일반 업체 관리는 유지된다. 거부 감사에 비밀정보가 남지 않는다.
- 검증 방법: 경로별 역할×대상 회귀 테스트와 MariaDB 경합 검증. 전시 대안: 새 관리자 화면의 검증된 범위만 설명하되 전체 관리자 경계 안전성은 주장하지 않는다.

## AUD-02 — 초기 최고관리자·데모 자격증명 분리 확인

- 현재 문제/근거: `deploy/ui-preview/seed_preview.py:12–18`은 새 시범 관리자/영양사/공급업체를 하나의 private demo secret으로 초기화한다. 이번에는 현재 비밀번호/해시를 읽거나 비교하지 않았다.
- 재현/확인: 소유자가 공유 이력과 관리자 전용 비밀 관리 상태를 안전하게 확인한다. 일반 계정 비밀번호가 공유됐다면 관리자 초기값도 노출될 가능성을 조사한다. 보고서/로그에 값을 쓰지 않는다.
- 기대 동작: 관리자 자격증명은 일반 시연 계정과 독립하고 기존 계정 자동 덮어쓰기 없이 명시적 승인 절차로만 변경.
- 관련 파일: seed, `accounts/views.py`, 계정 복구/운영 안내. 선행 조건: 계정 소유권·변경 승인. 기존 verify-admin 보존.
- 완료 기준: 관리자 비밀을 일반 사용자에게 안내하지 않으며 관리자 로그인·복구 책임자가 확인된다. 필요 변경은 사용자의 승인 후에만 수행한다.
- 검증 방법: 격리 seed 테스트·소유자의 비공개 운영 점검. 현재 동일 비밀번호라고 단정하거나 실제 로그인을 추측 시도하지 않는다.

## 후속 작업 선택 원칙

전시는 AUD-01~06의 위험을 우선 통제하고 AUD-20으로 증거를 확보한다. 상용 도입은 AUD-07~13/16/17과 시설별 수용 기준을 우선한다. AUD-14/15/19는 실제 범위/빈도에 따라 제외하거나 단계화할 수 있다. 모든 작업에서 기존 계정/데이터/AI 모델과 안정 브랜치를 보존하며 변경 승인 후 구현한다.
