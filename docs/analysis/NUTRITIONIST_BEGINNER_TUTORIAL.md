## 실제 화면과 콘텐츠

기존 `/procurement/workflow/` URL 및 `procurement:workflow`를 유지했다. `procurement/tutorial.py`에 콘텐츠, template에 표현, `guide.ts`에 읽기 인터랙션을 분리했다.

| 단계 제목 | 한 문장 설명 | 카레 사례 / 주요 이동 화면 |
|---|---|---|
| 1. 어떤 음식을 만들까요? | 먼저 언제, 어떤 음식을 만들지 정해요. | 11월10일 점심 카레라이스 / 주간 식단 작성 |
| 2. 몇 명이 먹을까요? | 식사할 사람 수를 예상하고, 준비할 최종 인원을 정해요. | 예상100명 → 최종100명 / 예상·최종 식수 관리 |
| 3. 어떤 재료가 얼마나 필요할까요? | 필요한 재료의 양을 보고, 부족한 만큼 공급업체에 주문해요. | 교육용 감자3kg·당근2kg·양파2kg / 소요량·발주예정서 |
| 4. 주문한 재료가 잘 도착했나요? | 도착한 재료의 수량과 상태를 확인하고, 사용할 수 있는 양만 등록해요. | 카레용 감자3kg의 수량·상태 확인 / 납품·검수 관리 |
| 5. 이제 음식을 준비해 볼까요? | 재료와 조리할 양을 확인하고, 조리할 사람에게 준비 내용을 전달해요. | 100명분 카레 조리지시서·메모 / 조리지시서 조회·수정·출력 |
| 6. 오늘 급식은 어떻게 마무리할까요? | 주문한 재료, 들어온 재료, 사용한 재료와 금액을 돌아봐요. | 카레 재료 입고·사용·금액 확인 / 월말 정산 검토 |

수량·날짜는 교육용이라고 그림 및 본문에 표시. 실제 레시피/영양 기준이 아니며 돈·영양값·AI 정확도를 만들어 표시하지 않았다. 일러스트는 직접 작성한 코드 기반 SVG로, 실제 화면 캡처인 것처럼 표현하지 않는다. 네트워크 이미지/외부 라이선스 자산을 추가하지 않았다.

화면 안내는 실제 template의 동작에 맞췄다. 특히 주간 식단은 메뉴 후보 클릭 즉시 저장, 사람 수는 「식수 저장」, 재료량은 「미리보기」→「발주예정서 저장」→「업체별 구매발주서 확정·저장」, 검수는 「검수 기록·확인」→「저장·확정」이다.

## 안전성과 역할

- 기존 독립 식수 관리·저장한 발주예정서·업무 메뉴·업무 URL·공급업체 포털·관리자·승인 정책 유지.
- 업무 화면별 기존 required_capability/can 기준으로 링크를 필터링한다. VIEWER는 허용 조회 화면으로 대체, COOK는 조리 링크를 제공하고 예측/발주 링크를 감춘다. 일반 SUPPLIER는 기존처럼 가이드403 및 전용 포털 유지.
- 「직접 해보기」는 GET 링크일 뿐이다. 클릭/읽음/진행률로 업무 데이터가 생기지 않는다. **이동 후 업무 화면에서 실제 입력·저장하면 업무 데이터가 바뀐다**고 버튼 바로 아래 안내한다.
- 분리된 사용자용 연습 모드/연습 데이터 생성 기능을 route·코드 탐색에서 확인하지 못했다. `/ui/compare/` iframe은 디자인 비교이지 업무 sandbox가 아니다. 이번에도 연습 모드/자동 합성 업무 데이터를 제품에 추가하지 않았다.
- `snp.guide.nutritionist.v1.<User PK>`와 `{current, completed}` 구조 유지. 수업 내용의 의미가 같은1~6단계를 유지하므로 기존 읽음 정보 손실 없음. 사용자별 분리, 초기화는 읽기 상태만 변경. 로컬 저장 차단 시 경고를 보여주고 현재 페이지 이동은 유지.
- 이전/다음 이동은 읽음 처리가 아니다. 「이해했어요」를 명시적으로 누른 단계만 진행률에 포함한다. 100%와 실제 업무 완료율을 구분한다.
- 단계 선택 후 제목 focus, 목록은 Home/End/좌우키/Enter, native details로 더 알아보기/FAQ 제공. JavaScript 없으면6단계를 펼쳐 읽고 기존 업무 링크를 사용할 수 있으며 동작하지 않는 진행 컨트롤은 숨긴다.
- Phase2-A는 아직 미배포다. 공개 가이드 콘텐츠에는 신규 `/deliveries/` 링크/반복 검수 사용 안내를 넣지 않았다. 관련 미완료 상황은 상세 설명에서 담당자 확인을 안내한다.
- AI 코드·모델·알고리즘·입력 파이프라인 및 업무 서비스·모델·migration은 변경하지 않았다.

Django365는 기존361 + 신규 초보자 가이드4개다. SQLite/MariaDB는 같은 케이스의 별도 실행이며 합쳐730고유 케이스로 부르지 않는다. SQLite7skip은 DB row lock 기능 차이, MariaDB는 모두 실행했다. JS/브라우저 지점도 Django 수에 더하지 않는다.

브라우저에서 단계별 실제 업무 링크를 눌러 도착 화면·뒤로가기·단계 복원을 확인했다. 읽기/이동/초기화 및 업무 화면 GET 동안 POST 요청0. 실제 업무 입력·저장 E2E를 이번 가이드 브라우저 테스트에서 수행한 것은 아니다. 기존 업무 쓰기 회귀는 전체 Django 테스트에 포함된다.

첫 브라우저 검증은 모바일 이동 버튼 높이가44px에 못 미쳐 실패했다. 원인은 기존 공통 CSS 우선순위였다. 기대값을 완화하지 않고 가이드 전용 selector를 강화한 뒤 실제48px 이상과 CTA 글자16px 이상을 검증했다. 마지막 문구 및 CSS 정리 뒤 targeted20/build/브라우저를 다시 확인했다. 전체 DB suite를 최종 CSS 조정 때문에 반복하지 않았다.

## 실제 초보자 1~2명 테스트 절차 (아직 미실시)

사전 준비: 별도 격리 서비스, 미리 승인한 합성 영양사 계정, 업무 데이터 저장 금지 안내. 실제 Preview 계정/발주로 연습하지 않는다. 참가자에게 가이드 URL만 알려주고 버튼 위치나 답을 설명하지 않는다.

| 과제 | 관찰·질문 | 기록 |

| 시작1분 | 무엇을 배우는 화면인지 말하고2단계로 이동 | 첫 행동까지 시간, 도움 요청 |
